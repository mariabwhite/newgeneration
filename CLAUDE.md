# Project Rules — ЭТАЛОН (UNIFIED DESIGN)

Этот файл — контракт для любого AI-агента, работающего в этой папке (Claude Code, Codex CLI, и др.). Читать ПЕРЕД любым действием с файлами.

## 1. Scope

- Работаешь ТОЛЬКО внутри этой папки: `САМАЯ УДАЧНАЯ КОПИЯ - ЭТАЛОН!`
- Не лезь в `..\` (соседние папки проекта) и не смешивай состояния разных копий.
- В GitHub НЕ пушишь без явной команды пользователя.
- Локальный git — твой друг. Коммить часто, после каждого осмысленного блока.

## 2. Параллельные агенты — стоп-сигнал

Если видишь свежие правки в файлах, которые не делал ты сам — это другой агент (Codex CLI, IDE-плагин, другой Claude). СТОП. Спроси пользователя.

Не пиши параллельно: 14 мая 2026 этим способом потеряли 24 урока Lab — Codex обрезал хвосты файлов одновременно с моими правками. Повторять не надо.

Признаки активного второго агента:
- В .git/ внезапно появляются `index.lock`, `HEAD.lock` и они не пропадают
- Только что прочитанный файл при перечитывании отличается
- В файлах появляются маркеры с временной меткой (типа `codex-a1-body-calm-20260514`)

## 3. Перед каждой записью

- Прочитай файл целиком (не фрагмент).
- Зафиксируй: размер в байтах, md5, последние 50 байт.
- Для HTML: проверь, что заканчивается на `</html>`.
- Для файлов с кириллицей: открой как UTF-8, проверь стабильность байтовой длины.

## 4. После каждой записи

- Перечитай файл.
- Сверь размер с ожидаемым (если дописал 100 байт — должно быть +100, не -500).
- Для HTML: проверь, что всё ещё заканчивается на `</html>`.
- Для CSS: если правка видимая — bump `?v=N` во всех HTML, которые его подключают. Иначе браузер увидит закэшированный старый файл и пользователь решит, что всё сломалось.
- После CSS-правок — проверь обе темы (dark + light).

## 5. Read-only зоны (НЕ трогать без явного разрешения)

- `_archive/` — версионные снапшоты, исторический архив
- `_internal/`, `_backups/`, любые `*.bak`, `*.broken`, `*.nullbackup-*`
- `audit-shots/` — Chrome profile dumps от Codex, не редактировать
- `cabinet/*.html` — кабинеты учеников/родителей/учителей
- `lingua-boost-lab/a1/`, `a2/`, `b1/`, `c1/`, `pre-a1/` — уроки Lab (только по явному запросу на конкретный урок)
- `assets/designs of lessons for kids/`, `assets/Для уроков/` — черновики DeepSeek

## 6. CSS refactor (домен J · унификация)

Самая чувствительная зона. Правила:

- Одна страница за раз. НИКОГДА пачкой.
- Снапшот до и после (минимум: размер + md5; идеально: скриншот в браузере).
- Старые CSS-классы оставлять как aliases в `legacy.css`, если на них завязан JS.
- Архитектура слоёв:
  - `system.css` — core, базовые токены и примитивы
  - `<page>.css` или inline `<style>` — только уникальные блоки страницы
  - `canon-L.css` — Lab-specific (не смешивать с system.css)
  - `legacy.css` — временные алиасы для старых классов
- Локальные `:root` на страницах должны исчезнуть — токены живут только в `system.css`.
- Тест в обеих темах после каждого шага.

## 7. Восстановление при поломке

Если файл оказался обрезан/побит:

1. Проверь git: `git log -- <файл>`, `git show HEAD:<файл>`. Самое надёжное.
2. Если в git нет — поищи в `_archive/`, `_backups/`, `_internal/backups/`. Будь осторожна: «свежий» бэкап может уже быть битым (история обрезок).
3. Если в бэкапах тоже битые — спроси пользователя. Не реконструируй молча.

## 8. Cyrillic / Edit tool

Edit tool иногда обрезает хвост файлов с кириллицей при кажущемся успехе. Поэтому:

- На больших файлах с кириллицей предпочитай Python через bash вместо Edit.
- ВСЕГДА после Edit/Write: `wc -c`, `tail -c 50`, `md5` — и сравни с ожидаемым.
- Если файл «съехал» — немедленно откат из git, не накатывай следующую правку.

## 9. Сомневаешься — стоп

- Не угадывай. Спроси пользователя.
- Не «доделывай интуитивно» — лучше один уточняющий вопрос, чем час откатов.
- Перед массовой операцией (>3 файлов) — покажи пользователю что собираешься делать, дождись «да».
